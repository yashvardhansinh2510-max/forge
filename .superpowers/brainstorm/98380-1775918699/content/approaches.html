How should the data work?

The app uses 100% mock data today. These 3 approaches differ in how "confirmed orders" feed the payments page.

A

Standalone mock store (isolated)

Create a new payments-data.ts with hardcoded orders. Payments page is completely independent — no connection to the sales module. Simplest and fastest.

Pros

  • Fastest to build
  • No dependencies

Cons

  • Data is not real — confirming a sales order doesn't actually update payments
  • Duplication of order data
B

Read from sales mock + add payment layer RECOMMENDED

Confirmed sales orders from sales-data.ts automatically feed the payments list. A Zustand store tracks payment transactions on top. When an order is confirmed in sales, it appears here automatically.

Pros

  • Orders appear automatically on confirmation
  • Single source of truth for order data
  • Right architecture for future DB migration

Cons

  • Slightly more setup
  • Need to add "confirmed" status to sales mock
C

Full API route with mock DB layer

Create /api/payments routes that simulate a real backend. Payments stored in-memory server-side. Most realistic simulation of a production system.

Pros

  • Most production-like
  • Easy to swap with real DB later

Cons

  • Resets on server restart (no persistence)
  • Overkill for a mock-first app
  • Doesn't match app's existing patterns

Click your choice, then confirm in the terminal. I recommend B.
